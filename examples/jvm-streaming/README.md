# Reproducible JVM streaming workload

This MIT example processes a deterministic corpus of 4,096 1 KiB messages with CRC32. It is a synthetic public workload with no broker, dependencies, private data, API keys, or paid model calls. It demonstrates allocation/copy costs and a throughput/latency batching tradeoff; it does not establish Kafka performance.

Install the product, then explicitly prepare the trusted JDK image outside the isolated workload:

```sh
python3 -m pip install -e .
docker pull eclipse-temurin:25-jdk
python3 examples/jvm-streaming/demo.py --output /tmp/autoresearch-jvm-proof
```

The demo uses only the Docker runner. It retains three independent JVM executions per variant and scenario, alternates variant order, then collects new baseline/candidate executions for independent confirmation. It reports inconclusive measurements honestly. The default one-second measurement/half-second warmup is a smoke demonstration; use longer, approved durations and an otherwise idle Linux runner for meaningful engineering conclusions. The image ID, JDK image version, Docker host/kernel, configured resource limits, and environment fingerprint are retained per execution. Remote runners accept `runner.docker_host = "ssh://user@linux-runner"`; SSH credentials stay in the Docker control client and do not enter workload containers. Remote SSH transport is implemented but not exercised by the local demonstration.

`avoid-copy.patch` removes the per-message payload copy. `batch-128.patch` processes 128 messages between boundary checks. Only `StreamProcessor.java` changes: the corpus, timer, independent CRC evaluator and correctness checks stay in protected `StreamWorkload.java`; `run.sh` is protected too. `campaign.json` provides a manual campaign contract for a standalone Git copy of this directory (`repository: "."`). Apply either patch only in a disposable copy of this directory, then execute `sh run.sh --duration 5 --warmup 2`. The demo generates variants in its own temporary directory and preserves this checkout.

Two scenarios use the same processor:

- Saturation (`--rate 0`, default) measures completed messages per elapsed second. It does not emit latency percentiles.
- Fixed arrivals (`--rate 10000`) schedules 10,000 messages per second. Every scheduled message is completed; latency starts at its scheduled due time and ends after CRC processing. Batching waits until the last scheduled message in the batch arrives. This includes batch queueing and producer scheduling delays and makes missed arrival times visible. The exact sorted nanosecond observations are retained; the per-run p99 uses nearest rank. The comparison uses independent per-run p99 values and does not claim a pooled percentile.

Correctness checks compare every processed message's CRC against an independently implemented bitwise CRC reference calculated before warmup. A completed-count check ensures the fixed-arrival run drains all scheduled messages. The reported error rate is zero because processing is synchronous and any checksum/count violation makes correctness fail and exits nonzero. These checks cover this synthetic transform and completion count; they are not a general application correctness proof. In a campaign, preserve the approved harness/checks and evaluate candidate code with independent protected checks.

The main thread's allocated bytes come from the JDK `ThreadMXBean`; this excludes sampler-thread allocations. Process CPU time comes from `OperatingSystemMXBean`. Heap usage and Linux RSS (`/proc/self/status`, `VmRSS`) are sampled approximately every 20 ms in the measurement window and written to `memory-series.json`; these are **sampled peaks**, not exact lifetime high-water marks or native-memory attribution. Unavailable RSS/allocation/CPU metrics are omitted. The JVM has a 256 MiB heap cap. RSS includes native memory, JIT and premeasurement state. Sampling is common to all variants, but its overhead is not separately quantified. The sampler retains its own small growing list of observations for export; it is part of this harness memory footprint. No p99 or RSS is inferred from other metrics.

`--duration 300 --warmup 2 --quiescence 2` requests a real five-minute saturation measurement followed by two seconds without processing. `measurement.elapsed_seconds` reports actual timed processing duration. `memory-series.json` contains only readings timestamped inside that window; the reported sampled peaks equal maxima of those readings. `memory-phases.json` retains requested/actual warmup and measurement durations, sample count, an immediate after-drain reading, and an after-quiescence reading. Processing is synchronous, so there is no queued asynchronous work to drain: every counted message has returned from the processor. The corpus and observation list intentionally remain live during quiescence. No forced GC occurs; these post-work readings do not estimate retained-live-object size or prove the absence of a leak. RSS metrics are omitted and artifact readings use `null` when unavailable. Quiescence defaults to one second and is bounded to 0–60 seconds.

The final diagnostic run sets `JFR=1` and collects a genuine `profile.jfr` using `-XX:StartFlightRecording=filename=...,settings=profile,dumponexit=true,maxsize=32m`. That run is separate from confirmation. Inspect it with `jfr summary /tmp/autoresearch-jvm-proof/diagnostic-jfr/files/profile.jfr`. A timeout may prevent dumponexit output; missing artifacts remain explicit. [JFR startup recording](https://docs.oracle.com/en/java/javase/25/jfapi/flight-recorder-api-programmers-guide.pdf).

The generic JMH adapter accepts the real JMH JSON result array. `jmh_command()` sets `-f` independent forks, `-wi` warmup iterations, `-i` measurement iterations, `-w`/`-r` durations, `-rf json`, `-rff` result filename, and `-foe true`. It retains raw values grouped by fork, their units, and percentile maps. Iterations are not independent JVM replicas and percentiles are not averaged. JMH performance output provides no correctness proof: `parse_jmh(..., checks=...)` requires separate evaluator checks before generic validation can accept it. Build dependencies into the trusted image before running because workloads have no network. [OpenJDK JMH CLI source](https://github.com/openjdk/jmh/blob/master/jmh-core/src/main/java/org/openjdk/jmh/runner/options/CommandLineOptions.java).

The runner filters common credential files and symlinks from source snapshots. Administrators must still review the selected source tree and trusted image: arbitrary secrets embedded in ordinary source cannot be automatically recognized. The container receives no host mounts, inherited environment, Docker socket, or network. CPU, memory, process count, workspace and artifact storage are bounded. A root-owned PID 1 timer cannot be signalled by the unprivileged workload and stops an orphan at the execution deadline plus up to ten seconds of artifact-collection grace; cleanup attempts are also bounded. Host mode is an explicitly trusted development option and provides no isolation from arbitrary host access; it kills the command process group, while Docker also terminates descendants that create independent process sessions.
